# Engineering decisions

This page explains the tradeoffs in the current SADA implementation. It is meant to be read alongside `app/live.py`, `app/streaming.py` and `web/app.js`.

## Why WebSockets instead of a simple upload endpoint?

The first prototype accepted whole utterances. That was fine for transcription, but it did not handle interruption well. The current client sends 20 ms PCM16 frames on a WebSocket, and the server emits `speech_started` and `speech_ended` events. That gives the browser a way to stop playback as soon as the next utterance begins.

## Why transcribe complete utterances?

Running recognition per audio frame would be expensive and often incoherent for a small local system. The VAD component groups frames and passes each completed utterance to faster-whisper. It is a pragmatic compromise: streaming transport with turn-level ASR, **not** partial transcript streaming. A future version could test a streaming ASR backend.

## Why are order actions not generated by the LLM?

Customer records and state-changing operations need predictable outputs. The intent engine handles synthetic order IDs and policy flows using Python, while the optional model only answers a limited set of general support questions. Keeping those separate makes the important behaviors easy to test and reduces accidental hallucinations.

## How does barge-in work?

A new speech-start event cancels the active server response task, and the client cancels the speech-synthesis queue. This is best-effort cancellation; a Whisper inference already running in a worker thread can continue in the background. Real concurrent-call deployments would need worker isolation and capacity limits.

## What can be measured now?

The test suite exercises API and workflow behavior, plus mocked audio and LLM streams. The 30 bilingual test examples are an intentionally small, hand-curated **intent regression check**. They do not establish real-world accuracy. End-to-end latency, word error rate across Arabic dialects, hallucination rate, concurrency and noise robustness require a device-specific benchmark set.

## Next improvements

1. Benchmark real Arabic and English microphone recordings in quiet and noisy environments.
2. Replace browser TTS with controllable local streaming speech output and measure first-audio latency.
3. Add session authentication and order-level authorization before any real CRM integration.
4. Introduce a small offline evaluation set covering mixed Arabic-English speech and interruptions.
5. Add structured tracing and latency breakdowns across VAD, ASR, routing, generation and synthesis.
